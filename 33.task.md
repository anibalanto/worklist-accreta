# Cubrir las formas de Spring que el censo de `hsi` no encontró

`--as spring-controller` cubre hoy lo que `hsi` usa, y sólo eso. `generators.rs` ya lista los seis nombres de anotación:

```rust
const MAPPINGS: &[&str] = &[
    "GetMapping", "PostMapping", "PutMapping", "DeleteMapping", "PatchMapping",
    "RequestMapping",
];
```

Así que la forma generalizada `@RequestMapping(method = RequestMethod.POST, path = "/x")` **ya funciona** a nivel método. Lo que falta son tres cosas que el censo del 2026-09-02 no encontró en `hsi` — cero casos de cada una:

## Las tres

**Controllers declarados en una `interface`.** `enclosing_class` sube hasta un `class_declaration` y nada más. Si el `@RequestMapping` de ruta está en una interfaz que el `Impl` implementa —el patrón "API interface + Impl"—, no encuentra clase, no captura el prefijo, **y el capture sale sin la mitad de la ruta sin decir nada**. Es el riesgo que [`chain.md`](../../subsystems/bilinker/commands/chain.md) ya nombra: *"un generador que acierta cuando no querías ya te escribió otra cosa, y un capture es opaco después."* De las tres, es la única que falla en silencio.

**Prefijo heredado.** Un controller que extiende una base anotada con `@RequestMapping` no ve ese prefijo.

**Dos grafías del mismo contrato.** `@GetMapping("/x")` y `@RequestMapping(method = RequestMethod.GET, path = "/x")` describen el mismo endpoint y hoy producen dos hashes distintos, así que pasar de una a la otra dispara drift sobre un contrato que no cambió. Hay que decidir si el generador normaliza o si son deliberadamente distintos.

## Por qué es backlog y no bloquea nada

El censo, sobre `bilinker-openapi` / `back-end/hospital-public-api`:

| | |
|---|---|
| `@RequestMapping` a nivel método | 0 |
| usos de `RequestMethod.` | 0 |
| controllers declarados en `interface` | 0 |
| controllers que heredan de una base | 0 |
| anotaciones con más de un atributo | 0 |

**Nada de esto puede dispararse en la adopción de `hsi`.** Vale como robustez para el día que el plugin se use en otro proyecto, y ahí la primera de las tres es la que importa, porque es la que no avisa.

## Qué toca

[`commands/chain.md`](../../subsystems/bilinker/commands/chain.md) § "`--as spring-controller`". El inventario de código sale de los no-OK.

## Dónde buscar las formas, en vez de esperarlas

> **Anotado el 2026-09-02.**

Este ítem concluyó que las formas raras *"no pueden dispararse en `hsi`, así que es backlog"*. **Eso es una conclusión sobre `hsi`, no sobre Spring**: el censo midió un dialecto, el de una sola empresa, y de ahí no se sigue que el generador aguante el siguiente repo.

Esperar a que se rompa con el próximo es la peor forma de enterarse, sobre todo si el próximo es de otra empresa.

**El corpus está publicado: los samples y los tests de Spring Boot.** Son dialectos escritos por quienes definen el framework, con las formas raras puestas a propósito — que es exactamente lo que a `hsi` le falta.

Y el criterio de éxito no hay que inventarlo: es el que [`34`](34.task.md) ya usó, y **corre solo sobre cualquier repo** — cada capture pertenece a exactamente un endpoint del censo por AST, y cada endpoint tiene exactamente uno. La biyección no depende de que alguien mire.
