# Poner a salvo los backups del corte y decidirles un hogar

**Va primera de las seis de [`43`](43.user-story.md), y es la única irreversible.** Todo lo demás se puede rehacer; esto no: si los backups se van, los 139 contratos se van con ellos y ninguna otra task tiene de dónde leerlos. No la necesita nadie para *empezar* —[`47`](47.task.md) y [`49`](49.task.md) no la esperan— pero [`4a`](4a.task.md) no puede correr sin ella.

Los 139 vecindarios que [`43`](43.user-story.md) restituye viven en los `.bilink-formato-3` de cada capa, y **eso no está versionado en ningún lado**:

```
$ cd ~/Workspace/hsi
$ git ls-files .bilink-formato-3        → 0
$ git check-ignore -v .bilink-formato-3 → .git/info/exclude:12:.bilink-formato-*
$ git ls-tree -r <ref> | grep -c formato → 0
```

Ni en la rama, ni en la ref, excluidos por el glob que puso [`3s`](3s.task.md). **Existen como archivos sueltos en un clon local y nada más**, así que reclonar o limpiar un árbol los borra — no hace falta que nadie cierre [`1x`](1x.task.md).

## Hecho el 2026-09-03: la copia existe

```
/home/anibal/Workspace/bilink-n1-backup-2026-09-03.tar.gz   144K
```

Las ocho capas, **excluyendo** el clon del proveedor de cada consumidor —`retinar` y `filasvirtuales` arrastraban 37 MB cada uno de `hsi/`, que se re-fetchea— y excluyendo `cache/` e `index/`, que son derivados. Verificado: **139 archivos con `n` adquirido adentro**.

> **Esta línea decía 165 y estaba mal**, corregido el 2026-09-02 contando el tarball con el mismo criterio. El tarball está bien —tiene los 139 que hay— y lo que estaba mal era el número contra el cual se lo verificó. De dónde salía, en [`43`](43.user-story.md) § *"No eran 165"*.

Es una copia de seguridad, no un hogar: está fuera de git.

## Decidido el 2026-09-02: se queda como tarball, y el hogar es de otro

**Las tres opciones que había:**

| | A favor | En contra |
|---|---|---|
| queda como tarball fuera de git | no ensucia ningún repo; ya está hecho | sigue sin versionar: una máquina, una copia |
| commiteado en accreta bajo `recovery/` | versionado y compartido; se borra al cerrar `43` | datos operativos en un repo de specs |
| commiteado en cada capa | viaja con lo que describe | el glob del exclude lo tapa; habría que exceptuarlo |

**Gana la primera, y el argumento es la ventana.** Este backup no tiene que sobrevivir mucho: [`4a`](4a.task.md) restituye y ahí deja de haber nada que custodiar. Montar un hogar versionado —con su excepción al glob o su directorio nuevo— es construir un mecanismo para un caso que se cierra en días, y **el mecanismo que hace falta no es para este backup sino para el próximo corte**.

Así que el hogar se escribió donde vale para todos: [`proposals/retencion-del-backup-del-corte.md`](https://github.com/anibalanto/accreta/blob/24da6745565b3452e42ebc750e30a46749855427/subsystems/bilinker/proposals/retencion-del-backup-del-corte.md), que es lo que [`1x`](1x.task.md) reclamaba y no tenía forma. La opción de `recovery/` está ahí, con la ref descartada y por qué.

**Queda un riesgo aceptado y conviene nombrarlo:** hasta que `4a` corra hay **una copia en una máquina**, más los `.bilink-formato-3` sueltos de cada capa. Lo que lo hace tolerable es que `1x` ya está bloqueado por [`43`](43.user-story.md) —*"no borrar todavía"*— así que el modo de falla que queda es un `git clean` o un reclone, no una limpieza deliberada.

**Y cuándo se puede borrar el tarball**: cuando `4a` haya restituido y las capas verifiquen.

## Qué toca

Nada de spec ni de código: queda como tarball. Lo que se escribió es la propuesta, y eso se ejecuta desde [`1x`](1x.task.md), no desde acá — forzarlo a esta task le pondría de dueño al backup de un corte una política que vale para todos.
