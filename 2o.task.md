# Error de conexión: `lspd` se muere cuando el language server manda una notificación que no conoce

Primera consulta real contra Java, con `jdtls` recién instalado:

```
$ lspd status
lspd  pid=545835  endpoint=/home/anibal/.lspd/daemon.sock
language servers:
  (ninguno arrancado todavía)

$ definitions sobre Svc.java
{"error":{"code":-32603,"message":"LSP initialize: ServiceStopped"}}
```

Y en el daemon:

```
[lsp] mainloop exited: Routing("Unhandled notification: language/status")
```

`jdtls` manda `language/status`, una extensión suya, **durante el handshake**. El router no la conoce, `async-lsp` lo trata como error de ruteo, y el mainloop se cae. El resultado es que **Java no funciona en absoluto**.

## No es de jdtls

El router enumera cuatro notificaciones y el comentario de al lado dice otra cosa:

```rust
// Server→client notifications (ignore all)
.notification::<notif::LogMessage>(…)
.notification::<notif::ShowMessage>(…)
.notification::<notif::Progress>(…)
.notification::<notif::PublishDiagnostics>(…)
```

*"Ignore all"* es lo que había que hacer y no es lo que hace: ignora **esas cuatro**. Cualquier otra mata la conexión.

**Y las extensiones son la norma, no la excepción.** `jdtls` manda `language/status` y `language/eventNotification`; rust-analyzer manda `experimental/serverStatus`; el de TypeScript tiene las suyas. Que hoy Rust ande es suerte: significa que rust-analyzer no mandó ninguna en el camino que probamos.

## La forma correcta

`async_lsp::router::Router` tiene exactamente esto:

```rust
.unhandled_notification(|_, _| ControlFlow::Continue(()))
```

Una notificación **no espera respuesta**: ignorar una que no se entiende es el comportamiento correcto del protocolo, no una concesión.

Con las **requests** es al revés y hay que tener cuidado: una request sin respuesta cuelga al servidor, así que `unhandled_request` tiene que **contestar un error**, no ignorar.

## Cuándo está hecha

- Una notificación desconocida no corta la conexión.
- Una request desconocida recibe un error y el servidor sigue.
- `definitions` sobre un `.java` contesta contra `jdtls` de verdad — hoy no llega ni al handshake.
- Hay un test que manda una notificación inventada y comprueba que el cliente sigue vivo.

## Lo que no entra

**Interpretar `language/status`.** Dice en qué anda el indexado de jdtls y podría alimentar un estado *"todavía indexando"* más fino que el de hoy. Es otra cosa, y primero hay que no morirse.
