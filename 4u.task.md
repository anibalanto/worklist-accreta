# Corregir `hierarchy.md`: una user story entra a un sprint entera, y el cálculo del backlog dice lo contrario

[`concepts/hierarchy.md`](https://github.com/anibalanto/accreta/blob/e4062baf835cf26165bf2f6536f38cadb2caf8a3/subsystems/worklist/concepts/hierarchy.md) se contradice a sí misma, y las dos mitades están a catorce líneas de distancia.

**§ La regla del ancestro** dice lo correcto:

> Una user story no puede atravesar sprints. Si entra, entra entera. Con lo cual una que no cabe en una iteración deja de ser algo que se parte en el planning y pasa a ser una user story mal dimensionada.

**§ El backlog no es un archivo** lo desdice:

> si las tasks de una user story están en sprints pero la user story no se nombra, la user story no está en ningún sprint. Está bien — el trabajo son las tasks, y la user story es agrupación.

Ese párrafo **habilita exactamente lo que la regla prohíbe**: partir una user story entre sprints, con sólo no nombrarla. Y no hace falta ningún truco para llegar ahí, porque la regla del ancestro tiene un agujero de redacción: *"sólo si ninguno de sus ancestros entra"* deja pasar una task suelta cuando su user story **no** entra a ninguno.

## Qué se decide, y no es una elección entre las dos

Gana la regla del ancestro, y el párrafo del backlog se va.

> **Lo que entra a un sprint es un subárbol entero.** Una user story entra con todas sus tasks o no entra. Una task se nombra sola sólo cuando no cuelga de ninguna user story.

Y la salida cuando una task no llega al sprint **no es dejarla afuera de su user story**: es reacomodar la descomposición — la task pasa a colgar de otra user story, o de ninguna. Eso ya está medio escrito en *"si una task se quiere sola pero cuelga de una user story, la pregunta no es cómo sacarla al sprint sino si está bien colgada de esa user story"*; falta que nombre el remedio y no sólo la pregunta.

## Por qué importa más de lo que parece

**La ambigüedad no falla.** Las dos lecturas producen planificaciones válidas y ningún comando puede distinguirlas: un sprint que nombra tres tasks de la misma user story se ve igual que uno que nombra tres tasks sueltas. El error no aparece hasta que alguien calcula el backlog y le da distinto que a otro.

Y el cálculo del backlog cuelga de esto: *"un ítem que no está referenciado por ningún sprint está en el backlog"* necesita saber **qué es lo referenciable**. Con el subárbol como unidad, un ítem está en el backlog si el tope de su rama no lo referencia ningún sprint, y eso tiene una sola respuesta.
