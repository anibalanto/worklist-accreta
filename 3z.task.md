# Error de cobertura: el vecindario de una firma resuelve a la firma misma, y el tipo que importa no se pregunta

`reach` decide en qué posiciones preguntarle al proveedor, y las toma del **byte inicial del nodo contenedor**:

```rust
for f in fields {                                  // rust: ["return_type", "parameters"]
    if let Some(child) = firma.child_by_field_name(f) {
        at.push(child.start_byte());
    }
}
```

El byte inicial de `parameters` es el paréntesis, y el de `return_type` es el tipo de más afuera. Ninguno de los dos es un tipo que se quiera vigilar.

## Medido

**El 2026-09-02**, aceptando `bilinker::check::check` con lspd en `READY`:

```rust
pub fn check(root: &Path, path: &Path) -> Result<Checked>
//          ^                            ^
//          |                            return_type → `Result` → anyhow, fuera de la capa: descartado
//          parameters → `(` → go-to-definition devuelve la función que lo contiene
```

El vecindario que quedó escrito:

```yaml
n:
  1:
    link: capture 5904724083b67ce568365a1028aa7c46   # (function_item name "check")
```

**El fragmento se declaró vecino de sí mismo.** Y `Checked` —el tipo por el que ese nivel 1 existe— no se preguntó nunca. Preguntándole al daemon en la columna de `Checked` a mano, contesta bien:

```
definitions check.rs 58 49  →  check.rs 26:11    # pub struct Checked
definitions check.rs 58 42  →  anyhow/src/lib.rs # Result, fuera de la capa
definitions check.rs 58 20  →  std/src/path.rs   # Path, fuera de la capa
```

O sea que **el proveedor no es el problema**: lo que está mal son las tres posiciones que se le pasan.

## Vale para los tres lenguajes, y para java a medias

`signature_fields` es `["type", "parameters"]` en java y `["return_type", "parameters"]` en rust y typescript. El campo del tipo de retorno acierta en java —`type` es el identificador— y falla en rust y typescript, donde `return_type` es el tipo compuesto. **`parameters` falla en los tres**: su byte inicial es siempre el paréntesis, así que los tipos de los parámetros no se preguntan en ningún lenguaje.

Lo que hay que recorrer son los **identificadores de tipo que el nodo contiene**, no su primer byte. `Result<Checked>` tiene dos, `(String, PathBuf, bool)` tiene tres, y `(a: Foo, b: Bar)` tiene dos más el paréntesis que no es ninguno.

## Lo que lo hace grave

**Un vecindario que se resuelve a sí mismo no falla: cubre.** El estado sale `OK`, el hash es real, el capture existe, y `check` no tiene con qué notar que lo que vigila es el propio fragmento. Es la familia de [`2r`](2r.task.md) un nivel más adentro: ahí un baseline sin vecindario decía `all clean`, y acá uno **con** vecindario dice lo mismo y tampoco vigila nada.

Y contesta al revés la pregunta que motivó el nivel 1: *"¿y si la edición cambió el tipo de retorno de A a B?"*. Hoy no — el tipo de retorno compuesto no se pregunta, y el hash del fragmento ya cubría su texto.
