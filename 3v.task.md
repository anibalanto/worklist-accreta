# `apply` recibe el puerto y mantiene `n.1.link`

`apply` repunta `link` cuando el fragmento se movió. Con el vecindario siendo captures, repunta también `n.1.link` — la misma operación N veces, y para los renames le alcanza git.

**Pero el conjunto gana y pierde miembros**, y ahí no:

```java
- public Dto get(String t)
+ public Dto get(String t, Filtro f)
```

De `{Dto}` a `{Dto, Filtro}`. Qué tipo es `Filtro` sólo lo sabe un language server, así que `apply` recibe el proveedor.

**Y con eso deja de haber excepción:**

> Todo comando que toque el eje del vecindario recibe el puerto, y **degrada sin él**.

Sin proveedor, `apply` arregla lo del fragmento con git y **dice que no pudo tocar el vecindario** — lo mismo que ya hace `accept`. La frontera del subsistema no se mueve: la librería sigue siendo git y tree-sitter.

## Sigue sin aprobar nada

Proponer un miembro nuevo deja el endpoint en `RELOCATED` y **no escribe ningún `accepted`**. `apply --dry-run` con proveedor lo dice antes de tocar nada:

```
n1: la firma menciona `Filtro`, que no está declarado — se agregaría
```

**Y no detecta que el tipo de retorno pasó de `A` a `B`**, que está adentro del fragmento y ya disparó `ALTERED` con tree-sitter. *"Ningún estado de aceptación se arregla solo."*

## Va después de [`3u`](3u.task.md)

`accept` es quien acuña los captures de los vecinos la primera vez. Sin eso no hay `n.1.link` que mantener.

`crates/bilinker/src/apply.rs` y el binario que le pasa el proveedor. La spec está en [`commands/apply.md`](../../subsystems/bilinker/commands/apply.md) § "Y mantiene el vecindario".
