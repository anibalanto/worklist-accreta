# Definir la `api` de bilinker, con su CLI como primer cliente

Es la que **fija la forma** que las otras dos van a copiar, así que las decisiones se toman acá.

Hoy `crates/bilinker` expone todo lo que quedó `pub`: `bilink_ref::Repo`, `BiLink::load`, `Capture`, los estados, los módulos de cada comando. Un consumidor puede hacer cualquier cosa, incluido parsear el formato — que es lo que [ADR-0001](../../subsystems/impact/.stratum/impl/docs/adr/0001-orquesta-no-escribe.md) prohíbe.

## Qué expone

**Los verbos, y nada más.** Un módulo `api` cuya superficie sea la de la línea de comandos:

```
check · accept · apply · get · history · verify-ref
capture · chain · recapture · remove
sync · push · pull · adopt · track · relayer · init
```

Cada uno con sus argumentos como tipos y su resultado como struct. Nada de `&str` donde hay un uuid, un endpoint o un estado.

### `graph` es el verbo que hay que mirar con cuidado

Hoy `bilinker graph` hace dos cosas que no son la misma:

| | De quién |
|---|---|
| **resolver una cadena a la capa vecina** y emitir el nodo ya canónico | de bilinker — [`node.md`](https://github.com/anibalanto/accreta/blob/209d0d9d9d4025554450228c5a31175fa47511e1/subsystems/lattice/concepts/node.md) lo dice: *"porque la topología de cadena es conocimiento de su formato"* |
| **saltar de un fragmento a los otros bilinks de ese fragmento** (`--depth`, BFS) | eso es **componer**, y componer es de lattice |

**Definir el verbo en la api decide la frontera sin discutirla.** Si `graph` en la api es *"las aristas que este contenedor contiene"* —la consulta por contención de [`30`](30.task.md)—, el multi-hop queda afuera solo, y el CLI decide aparte si lo sigue ofreciendo por compatibilidad.

No hay que sacar nada antes: `--recursive` lo usa lattice y funciona, y moverlo pediría meterle a lattice una dependencia de stratum para ganar poco. **Atravesar capas para resolver un endpoint tampoco se toca** — eso es leer el formato, no recorrer un grafo, y es lo que hace `get` hoy.

## Y lo que **no** expone

**Los tipos del formato.** Si `api` reexporta `BiLink` o `Capture`, la regla de ADR-0001 pasa de estructural a disciplina — y ese es el único costo real de dejar de invocar procesos.

Un consumidor que necesite el formato tiene `bilink-format`, que es un crate aparte con su esquema publicado, hecho **exactamente** para eso.

## La CLI se reescribe contra la api

No es un extra: es la prueba. Si la CLI puede hacer su trabajo sin tocar nada fuera de `api`, la api está completa; si no, falta algo, y se ve al escribirla.

Hoy la CLI arma sus propias structs y llama a los módulos directo. Después de esto, `main.rs` es parseo de argumentos, una llamada, y formateo — **y el formateo es lo único suyo.**

De ahí sale un beneficio que hoy es deuda: el `--format json` deja de ser una segunda implementación y pasa a ser serializar lo que la api ya devuelve.

## Cuándo está hecha

- `crates/bilinker/src/api.rs` expone los verbos con tipos, y ninguno de los tipos del formato.
- `bilinker-cli` no importa nada de `bilinker::` que no sea `api`.
- Un test que compile un consumidor mínimo contra `api` y **no** pueda cargar un bilink.
- La superficie de la api cubre todo lo que la CLI ofrece: ningún comando quedó con lógica propia.

## Lo que no entra

Cambiar qué hace ningún comando. Es una reorganización de la superficie, no de la conducta — y eso se verifica solo, porque los 163 tests de integración corren contra la CLI.

## Dónde se escribe la api, antes de moverla en el código

> **Anotado el 2026-09-02.** Los cuatro puntos de "cuándo está hecha" hablan de `api.rs`, de imports y de un test. **Ninguno de un documento**, y el método de este proyecto dice tocar la spec primero.

La superficie de la api no está declarada en ningún lado, y el lugar natural es [`architecture.md`](https://github.com/anibalanto/accreta/blob/209d0d9d9d4025554450228c5a31175fa47511e1/subsystems/bilinker/architecture.md). **Hay que escribirla ahí antes de moverla en el código**, o el inventario de no-OK no dice nada sobre lo que es la reorganización más grande del subsistema.

Y hay una razón práctica además de la de método: los 163 tests de integración corren contra la CLI, así que **si la conducta no cambió se sabe solo**. Lo que esos tests *no* contestan es si la api quedó angosta —si no reexporta `BiLink` ni `Capture`—, que es lo único caro de esta task, porque es lo que vuelve estructural la regla de [ADR-0001](../../subsystems/impact/.stratum/impl/docs/adr/0001-orquesta-no-escribe.md) en vez de disciplina. El test del consumidor mínimo es el que importa, y un documento que diga qué entra y qué no es lo que lo hace verificable.
