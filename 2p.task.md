# Error de resolución: `definitions` contra `jdtls` devuelve vacío aunque el servidor esté RUNNING

Con [`2o`](2o.task.md) arreglado, el handshake anda:

```
$ lspd status
language servers:
  jdtls                       RUNNING  queries=1
```

Y la consulta no devuelve nada:

```
definitions Svc.java:1:11   →   {"result":[]}
```

Sobre dos archivos triviales —`Svc.java` con `public Dto get()` y `Dto.java` al lado—, apuntando a la `D` de `Dto`. Cuatro intentos con hasta 65 segundos de espera, con y sin layout `src/`. Siempre vacío.

**Un vacío es indistinguible de "no hay definición".** Ése es el problema de fondo: `lspd` contesta bien-formado, y quien pregunta no tiene cómo saber que no se resolvió nada.

## Hipótesis, sin verificar

Hay que confirmar cuál antes de arreglar nada:

| | |
|---|---|
| **falta `-data`** | el launcher acepta un directorio de workspace y el wrapper no le pasa ninguno; puede estar usando uno compartido o inservible |
| **el proyecto invisible no se armó** | `jdtls` necesita reconocer un proyecto para tener classpath. Dos `.java` sueltos pueden no alcanzar — y `hsi` es Maven, así que el caso real puede andar donde éste no |
| **el `didOpen` no alcanza** | se abre `Svc.java` y nunca `Dto.java`; sin el segundo en el modelo, la definición no está |
| **sigue indexando** | 65 segundos es poco para `jdtls` en frío, aunque para dos archivos sería mucho |

La tercera es la más barata de probar y la que más se parece a un defecto nuestro.

## Y hay algo que arreglar aunque la causa sea de jdtls

**`lspd` no distingue "no hay definición" de "no pude resolverla".** Es la misma confusión que el ecosistema persigue en todos lados —`Degraded` en lattice, `CONTRACT_UNVERIFIED` en bilinker— y acá está en la base: si el servidor está indexando, la respuesta correcta no es `[]`.

`jdtls` manda `language/status` justamente para eso, y [`2o`](2o.task.md) la dejó ignorada a propósito. Leerla es lo que permitiría contestar *"todavía no sé"*.

## No es de `jdtls`, y lo que provoca es peor de lo que decía acá

> **Medido el 2026-09-02**, con `rust-analyzer` sobre el impl de bilinker, al levantar `lspd` para aceptar los 39 endpoints que quedaron de [`3c`](3c.task.md).

**Lo mismo, en otro lenguaje.** `lspd status` decía `rust-analyzer RUNNING`, y `definitions` sobre la firma de `chain_new` devolvió `[]` mientras el servidor todavía indexaba —19% de CPU, 1,3 GB de RSS, y siete minutos hasta aflojar—. Con lo cual **la causa no está del lado de Java**: las dos hipótesis específicas de `jdtls` de acá arriba —el `-data` y el proyecto invisible— dejan de poder ser la explicación entera, y la cuarta —*"sigue indexando"*— queda confirmada como suficiente para producirlo.

**Y no queda en `CONTRACT_UNVERIFIED`**, que es lo que este ítem decía más abajo. Un `[]` no llega a bilinker como *"no pude mirar"*: el puerto distingue `None` de `Some(vec![])`, y `lspd` contestando bien-formado da lo segundo. De ahí:

```rust
// neighbours::fold sobre una lista vacía
hash:     e3b0c442…b7852b855   // sha256("")
hash_ast: e3b0c442…b7852b855   // ídem, y `every_one_has_a_grammar` vale vacuamente
```

Eso se escribió en el bilink **como vecindario adquirido**:

```yaml
n:
  1:
    hash:     e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
    hash_ast: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

**Un baseline que afirma una cobertura que no tiene, que es exactamente lo que [`2r`](2r.task.md) existe para impedir.** `2r` cerró el caso *"sin proveedor, mudo y sin decirlo"*; éste es *"con un proveedor que todavía no sabe, vacío y diciendo que miró"*. La aceptación se revirtió a mano —`update-ref`, el archivo y `.bilink/head`— porque no hay comando que deshaga un `accept`.

**Y no hay guarda posible del lado de bilinker.** Un vecindario vacío **es legítimo**: una firma que sólo menciona primitivos no tiene vecinos. Así que *"no hay tipos que resolver"* y *"todavía no indexé"* son la misma respuesta, y el único que puede distinguirlas es quien tiene la notificación de estado. Eso deja el arreglo firmemente de este lado.

**Lo que bloquea, además de `hsi`:** aceptar el impl de bilinker. Los 39 no-OK no se pueden cerrar con vecindario hasta que esto esté, y cerrarlos sin él es la decisión de [`3h`](3h.task.md).

**Lo que no se probó:** si con el servidor ya indexado `definitions` contesta. Se bajó `lspd` antes de reintentar, así que queda abierto si el `[]` es sólo de la ventana de indexado o también después — que es la diferencia entre un defecto transitorio y el de este ítem.

## Por qué importa para la adopción

El cierre de firma sobre `hsi` **depende de esto**. Sin `definitions`, `hash_n1` no se puede calcular y todo queda en `CONTRACT_UNVERIFIED` — que no falla, pero deja sin cubrir la mitad del caso de [`1d`](1d.task.md).

**Probarlo contra `hsi` y no contra un ejemplo.** Es un proyecto Maven real, que es el caso que importa y puede comportarse distinto que dos archivos sueltos.

## Cuándo está hecha

- `definitions` sobre un tipo de un proyecto Java real devuelve su declaración.
- Está identificada la causa del vacío, no tapada con un reintento.
- Un servidor que todavía no puede contestar **no devuelve `[]`**: lo dice.

## Lo que no entra

**El estado fino de indexado.** Interpretar `language/status` para decir *cuánto* falta es otra cosa; acá alcanza con distinguir "no hay" de "no sé".
