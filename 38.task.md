# Error de aceptación: `--no-n1` se ignora cuando hay un proveedor de vecindario respondiendo

`accept --no-n1` sobre un fragmento con firma resoluble **escribe un `n1` adquirido** si hay un `lspd` escuchando, en vez de la renuncia que se pidió. El flag no se mira.

La resolución del vecindario no consulta `no_n1` — depende sólo de que se esté aceptando contenido y de que haya proveedor:

```rust
let folded = match (what.content, nb) {
    (true, Some(p)) => p.of(layer, &cap.file, &range)?
        .map(|locs| crate::neighbours::fold(layer, &locs))
        .transpose()?,
    _ => None,
};
let neighbourhood = resolve_n1(layer, &cap, &range, previous, &folded, what, &content_hash)?;
```

Y `resolve_n1` retorna antes de llegar a la tabla que decide:

```rust
if let Some(f) = folded {
    return Ok(Some(N::of_level_1(f.clone())));
}
```

`what` entra a la función y para este camino no existe. **La renuncia sólo se respeta cuando el proveedor está caído** — o sea, exactamente en el caso en que no hacía falta pedirla.

## Es la simétrica de [`2r`](2r.task.md), y rompe la misma invariante

`2r` cerró el caso *"el ambiente decide por vos hacia abajo"*: sin daemon el baseline nacía mudo sin que nadie lo hubiera elegido. Esto es el mismo defecto hacia arriba — **con daemon, la decisión de la persona se pisa sin decirlo.**

Y se lleva puesta la **invariante 4**, que es la que `2r` invocó para que el flag dejara marca: *"aceptar el mismo fragmento en el mismo estado produce siempre los mismos valores de `accepted`"*. Hoy el mismo comando, sobre el mismo fragmento, escribe `n1: declined` o un `n1` adquirido según si había un language server prendido en esa máquina. La determinación la vuelve a tomar el ambiente; sólo cambió de lado.

## La fila que la tabla de `2r` no tiene

Aquella tabla cruza *"ya tiene `hash_n1`"* con *"daemon"* y con *"la firma cambió"*, y todas sus filas con daemon presente asumen que no se renunció:

| Ya tiene `hash_n1` | Daemon | `--no-n1` | hoy | debería |
|---|---|---|---|---|
| no | **sí** | **sí** | escribe `n1` adquirido | `n1: declined` |
| sí | **sí** | **sí** | recalcula y lo pisa | pide `--no-n1 --force`, como sin daemon |

La segunda fila es la peor de las dos: `(true, true, true, _)` ya está resuelta en la tabla del código —bajar una cobertura que estaba se pide entero, con `--force`— pero **nunca se llega**, porque `folded` retornó antes. El guard escalonado que `2r` argumentó existe y es inalcanzable con el daemon vivo.

**Que `--no-n1` gane siempre** es además lo más barato: si está el flag, no hace falta preguntarle nada al proveedor, y se ahorra el RPC.

## Se ve en la suite, y por eso se encontró

Con un `lspd` escuchando, los tests de integración que aceptan dos veces el mismo vínculo fallan: el primer `accept --no-n1` escribe un `n1` adquirido en vez de la renuncia, y el segundo entra por `(had: true, no_n1: true, force: false)`, que hace `bail!`. No se escribe nada, y el helper `accepted_of` panickea con *"el endpoint está aceptado"*.

**Observado el 2026-09-01**, sin haberlo buscado: una corrida con el daemon vivo dio `146 passed; 38 failed; 1 ignored`, y la misma suite sobre el mismo árbol, con el daemon muerto, dio `184 passed; 0 failed`. La sesión que lo produjo se cortó antes de poder atribuirlo, y el diagnóstico salió de leer el código.

Que la suite pueda alcanzar el daemon de la máquina es un defecto aparte: [`39`](39.task.md).

## Qué toca

[`commands/accept.md`](../../subsystems/bilinker/commands/accept.md) y [`concepts/accept.md`](../../subsystems/bilinker/concepts/accept.md): la tabla que `2r` dejó escrita no tiene la columna de la renuncia, así que las dos filas de arriba no están dichas en ningún lado — el código las decide por omisión. El inventario de código sale de los no-OK.
