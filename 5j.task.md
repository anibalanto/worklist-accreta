# Error de alcance: borrar una rama entra a los hooks como un push y `assign-keys` le pide el árbol al sha nulo

Borrar una ventana del servidor —`git push srv :secure/sprint/1`— funciona, y en el camino escupe:

```
remote: Error: git ["ls-tree","-r","--name-only","0000000000000000000000000000000000000000"]
        fallo: fatal: not a tree object
```

Un borrado llega a `pre-receive` y `post-receive` como cualquier otra línea, con **`new_rev` en ceros**: es la convención de git para *"esta ref deja de existir"*. Los hooks no la distinguen y siguen como si hubiera contenido nuevo que resolver.

## Qué tan grave es, con precisión

**Hoy, poco**: el borrado se completó igual, porque `post-receive` no puede rechazar nada. El costo es un error en la salida de una operación que salió bien, que es exactamente lo que enseña a ignorar la salida.

**Y hay una mitad que no probé**: `pre-receive` **sí** puede rechazar. Si `check-push` tropieza con el sha nulo en vez de dejar pasar el borrado, borrar una ventana sería imposible — y eso importa porque [`5d`](5d.task.md) decidió que las ventanas no se cierran solas, así que borrar una a mano es la única forma que queda.

## Lo que hay que decidir

**Qué significa borrar una rama para el proveedor: nada.** Una ventana es derivada, y que deje de existir no dice nada de los issues. Así que los dos hooks tendrían que reconocer el sha nulo y no hacer nada — ni asignar, ni verificar.

**Y si `insecure/**` se puede borrar.** El panorama no se puede empujar por diseño; borrarlo es otra operación y hoy nadie dice si se puede. Vale enunciarlo en la grilla de clases de ref, que es donde ya está escrito qué hace `pre-receive` con cada prefijo.

## Cuándo está hecha

- Borrar una ventana no imprime ningún error.
- `check-push` deja pasar el borrado de una `secure/**` — con un test, no probándolo a mano.
- La grilla de clases de ref de `sync.md` dice qué pasa con un borrado.

## Corrió, y la mitad que faltaba resultó ser la grave

Lo que este ítem decía: *"hay una mitad que no probé: `pre-receive` **sí** puede rechazar"*. Se probó sola, y rechazaba.

Mientras el compare-and-swap sólo miraba el tip anterior, el sha nulo no le llegaba nunca. [`61`](61.task.md) lo hizo mirar también el revisión que llega, y ahí `git diff --name-only <old> 0000…` falló con `bad object` — **y el borrado de una ventana pasó a ser imposible**. Que importa porque [`5d`](5d.task.md) decidió que las ventanas no se cierran solas: borrar a mano es la única vía que queda.

Arreglado en los tres lugares donde el sha nulo llega: `check_one` no verifica un borrado, `changed_keys` no le pide el diff, y `assign_window` no le busca un árbol. **Borrar una rama no escribe nada en el proveedor**, así que no hay nada que probar ni que resolver.

Con un test que lo fija: el proveedor tiene un status que *divergiría*, y el borrado pasa igual.
