# El worktree local no trae lo que el servidor escribió, y re-cortar la ventana lo descarta

Un push a una ventana deja el `.worklist/secure/sprint/<n>` local **atrás**. El servidor renombra `1.epic.md` a `ACC-14.epic.md`, reescribe las referencias y agrega los `normalize:`, y todo eso queda en la rama del servidor: parado en el worktree, los archivos siguen teniendo su slug base-36.

Hoy no hay flujo para traerlo. **Ninguna rama tiene upstream** —el bare se clonó del repo local y nunca hubo `--set-upstream`—, así que ni siquiera `git pull` a secas funciona.

## Y el atajo que usé es peor que el problema

Durante los diez pushes volví a cortar la ventana con `worklist window open <n>` cada vez que necesitaba el estado limpio. Eso **corta de nuevo desde el panorama**, que sigue teniendo los slugs, así que **descarta lo que el servidor escribió**: los renombres, las referencias reescritas y los `normalize:`.

Sirvió porque estaba cargando, no trabajando — no había nada local que perder. En cuanto alguien edite un ítem en su ventana, re-cortar es perder su trabajo.

> **Re-cortar es para abrir una ventana. Traerla al día es un `pull`, y son operaciones distintas.**

## Lo que hay que decidir

**Si el push deja el upstream puesto.** Un `worklist window open` que además configure el remoto y la rama de seguimiento haría que `git pull` alcance, sin comando nuevo. Es lo más chico que resuelve el caso.

**Qué pasa con lo que el cliente tenía sin pushear.** El servidor commitea encima —`rename`, `normalize:`— así que un `pull` normal es un merge o un rebase de lo local sobre eso. Con el worktree limpio es un fast-forward; con cambios locales, no. Vale decidirlo antes de que pase.

**Y si conviene un comando propio.** `worklist window sync` podría traer, verificar que la rama sigue siendo la que el proveedor dice, y avisar. Es más superficie, y la alternativa es que sea git pelado y que el modelo no se meta.

## Cuándo está hecha

- Después de un push, traer la ventana al día es **una** operación, y los archivos quedan con su clave.
- `window open` sobre una ventana que ya existe **no descarta** en silencio lo que el servidor escribió: o lo dice, o no lo hace.
- El flujo está escrito donde alguien lo va a leer antes de perder trabajo.

## Corrió

**Recortar sobre una ventana viva ahora es un error y no escribe nada:**

```
Error: secure/sprint/10 ya existe y tiene 1 commit(s) que este corte no contiene
  8ec31e2 window: sprint/10 recortado desde insecure/all

recortar de nuevo los descarta. Para traer lo del servidor:
    git fetch <remoto> && git merge --ff-only <remoto>/secure/sprint/10

Para descartarlos igual: --force
```

**Y traer anda**, que era la otra mitad:

```
$ git fetch srv secure/sprint/10 && git merge --ff-only FETCH_HEAD
 rename 4j.task.md => ACC-95.task.md (85%)
 rename 4i.task.md => ACC-96.task.md (86%)
```

Fast-forward, sin comando nuevo. El servidor commitea encima en vez de reescribir, así que el caso sano siempre lo es — y que no lo sea es la señal de que la rama divergió, que es justo lo que un merge automático escondería.

### Por qué `git pull` a secas no andaba: faltaba el upstream

No era el modelo: era configuración. El bare se clonó del repo local y **ninguna rama tenía rama de seguimiento**, así que `git pull` fallaba con *"no hay información de rastreo"* y había que escribir el remoto y la rama a mano.

Configurado una vez —`git branch --set-upstream-to=srv/secure/sprint/<n>`— las diez ventanas se traen con `git pull --ff-only` y nada más:

```
sprint/1    rename w.task.md => ACC-25.task.md (95%)
sprint/7    rename m.task.md => ACC-93.task.md (64%)
…
```

**82 archivos, todos nombrados por su clave, y ninguno sin.**

Quedó hecho a mano. Que `window open` lo deje puesto al crear la rama es lo que falta para que no haya un paso que alguien tenga que saber — es chico y es de este ítem, no de otro.

## La tercera cara, que no estaba en el enunciado

Probando el `merge` apareció: **`update-ref` mueve una rama aunque tenga un worktree checkouteado.** `git branch -f` se niega; `update-ref` no, y deja ese worktree con el índice del árbol anterior.

El síntoma no dice la causa. `git status` muestra archivos *"modificados"* que nadie tocó, y el `merge` se niega por cambios locales que no existen. Me llevó una vuelta entera de diagnóstico entender que lo que parecía trabajo perdido era un índice desactualizado — y eso fue **sabiendo** lo que había hecho.

Ahora se niega, **y ni siquiera con `--force`**: forzar autoriza descartar commits a sabiendas, no dejar un checkout inconsistente. Son dos cosas distintas y el flag sólo cubre una.

## Lo que queda abierto, y no es de esta tarea

**Quién corta la ventana.** [`5a`](5a.task.md) dijo *"un comando que el servidor puede invocar"* y en esta sesión las corté yo en el bare local. Si el servidor corta y el cliente sólo trae, este defecto **no existe** en vez de estar guardado. Es una decisión del montaje real y va con [`5v`](5v.task.md).

**Y cuál es la fuente.** El bare local tiene dos remotos: GitHub y el servidor de sync. El servidor es el único que corre los hooks, así que es el único que puede prometer consistencia con el proveedor — pero eso no está decidido ni escrito.

Cuatro tests nuevos: la negativa nombrando el commit que se perdería, que `--force` sí recorta, que una ventana nueva no se bloquea, que re-cortar una intacta tampoco, y el del worktree checkouteado.
