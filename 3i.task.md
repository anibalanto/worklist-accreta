# Error de protocolo: `lspd` contesta `-32603` donde su spec dice `-32000`

La tabla de [`protocol.md`](../../subsystems/lspd/concepts/protocol.md) declara cuatro códigos, y uno de ellos no es el que el daemon manda:

| la spec dice | el código manda | cuándo |
|---|---|---|
| `-32000` | **`-32603`** | el language server falló o no hay soporte para ese lenguaje |

Es la única constructora de `types.rs` que no coincide:

```rust
pub fn server_error(id: serde_json::Value, msg: String) -> Self {
    Self::err(id, -32603, msg)
}
```

## Medido

**El 2026-09-02**, al agregar `-32001` en [`2p`](2p.task.md). Se buscó dónde estaba `-32000` para poner el nuevo al lado, y no estaba en ningún lado: `grep -rn "32000" crates/` no devuelve nada.

## Por qué no es cosmético

`-32603` es **`InternalError` de JSON-RPC**, un código reservado del estándar. `-32000` a `-32099` es el rango que JSON-RPC deja libre para errores de aplicación, y por eso `-32001` —el que `2p` agregó— cae ahí.

Con lo cual hoy conviven dos convenciones en la misma tabla: un error de aplicación usando un código reservado, y otro usando el rango correcto. **Un consumidor que quiera distinguir "el daemon no pudo" de "el daemon se rompió parseando" lee la spec, matchea `-32000`, y no matchea nunca.**

Y es exactamente la clase de cosa que `2p` acaba de argumentar: la tabla de códigos existe para que nadie tenga que matchear prosa. Una tabla que miente sobre un código es peor que no tenerla, porque se le cree.

## Cuál de los dos se mueve

**El código, no la spec.** `-32603` está mal por el estándar, no sólo por la spec: un language server que no arranca no es un error interno del daemon, es la respuesta a esa pregunta. Y `-32001` ya quedó publicado en el rango de aplicación, así que mover la spec a `-32603` dejaría los dos códigos del daemon en rangos distintos por ninguna razón.

**Y hay que mirar si alguien lo matchea.** El único consumidor con lógica por código es hoy `lspd-client`, y sólo mira `NOT_READY`; el resto trata cualquier error igual. Así que el cambio no debería costar nada — pero eso hay que verlo, no suponerlo.

## Qué toca

Nada de la spec: la spec ya dice lo correcto. Es el único caso hasta ahora donde el no-OK va a salir de que **el código se movió hacia la spec** en vez de al revés. El inventario sale de los no-OK igual.
