# Error de detección: `acli` devuelve éxito cuando falla, y el hook subió cinco descripciones rechazadas sin decir nada

El primer push real de una ventana —`secure/sprint/1`— reportó cinco asignaciones correctas y terminó bien. En Jira los cinco issues existen con el tipo correcto. **Y los cinco tienen por descripción su propio título**, porque las cinco llamadas a `set_description` fallaron y ninguna se reportó.

```
$ acli jira workitem edit --key ACC-16 --description-file cuerpo.json --yes
✗ Failure: ACC-16 can't be edited: InvalidPayloadException: INVALID_INPUT
$ echo $?
0
```

**El error va a `stdout` y el exit code es 0.** `set_description` mira `out.status.success()`, que es `true`, así que no hay nada que hacer `bail!`. El hook llegó al final, escribió el `update-ref` y el push salió limpio.

## Por qué es el más grave de los tres

Es el que **esconde a los otros dos**. El cuerpo rechazado ([`5g`](5g.task.md)) y la jerarquía que no viaja ([`5h`](5h.task.md)) son defectos de contenido; éste es el que hizo que se descubrieran mirando Jira a mano en vez de leyendo la salida del push.

Y contradice lo que el resto del sistema hace: `check-push` existe para **fallar hacia reportar**. Un `post-receive` que no puede rechazar el push tiene una sola obligación, que es decir lo que pasó.

## Lo que hay que decidir

**Cómo se detecta.** El exit code no sirve, así que queda mirar el `stdout` — un `✗ Failure` o el `InvalidPayloadException`. Es frágil: depende del texto de una herramienta ajena, y de su idioma. La alternativa es **verificar el efecto**: leer la descripción de vuelta y comparar, que es caro pero no depende de cómo `acli` decida escribir sus errores.

**Y qué hace el hook cuando falla.** No puede rechazar el push —ya está aceptado—, así que sus opciones son dejar el issue con la descripción mal y reportarlo fuerte, o no renombrar el archivo para que el ítem siga siendo un pedido y el próximo push reintente. La segunda deja el repo consistente con Jira; la primera deja la clave, que ya está asignada de todos modos.

## Cuándo está hecha

- Un `set_description` que Jira rechaza hace que el push **lo diga**, con la clave y el motivo.
- Hay un test que lo cubre sin Jira: un `Creator` de prueba que devuelve exit 0 con `✗ Failure` en stdout.
- Los cinco issues del sprint 1 tienen su cuerpo real.
